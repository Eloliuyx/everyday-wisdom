# Everyday Wisdom — V1 开发里程碑与上架指南

状态：已开始实施；实际完成状态见 [RELEASE_READINESS.md](RELEASE_READINESS.md)。官方流程已于 2026-09-24 核对；正式提交前再核对一次。

## 1. 已确定的产品

**Everyday Wisdom 为 Obsidian Daily Notes 提供每天一条、按日期固定的英文日常沉思。**

- 名称：Everyday Wisdom。
- 拟用插件 ID：`everyday-wisdom`。名称和 ID 是否可注册仍需在 M1 核实；当前不宣称已预留。
- 仓库名：`everyday-wisdom`；本地目录为 `~/Documents/obsidian-code/everyday-wisdom`。
- 内容基础：[v0.4 JSON](../src/content/wisdom.json) 与[完整阅读版](CONTENT.md)。
- 内置 366 条；302 条有可选问题，64 条只有短文。
- 沿用 v0.4 的 12 个月主题，不采用旧 PRD 的佛教主题安排或每日来源标签。
- 英文界面与英文内容；本地运行、离线可用，无账号、遥测或远程内容请求。用户主动打开支持链接时才离开插件访问网站。
- 面向桌面、iOS 和 Android；平台验证必须记录实际环境。
- 与 Everyday Classical Music 保持独立，不把其维护任务并入本项目。

产品介绍建议：**Add one thoughtful reflection to each date in your Daily Notes, entirely offline.**

V1 包含自动插入、手动插入、防重复、按日期范围补齐已有日记、批量移除、小型设置页和可选支持链接。音频、随机换一条、AI 生成、打卡、账号、内容商店和自建同步服务不进入本版。

## 2. 推荐采用的行为细则

以下是本计划的实现基线，在 M1 写入更新后的产品规格。

| 情境 | 预期行为 |
| --- | --- |
| 新建能够识别日期的 Daily Note | 自动插入该笔记日期对应的短文，包括明确创建的过去或未来日记。 |
| 打开今天已有的 Daily Note | 自动补入缺少的短文；已有标记则不修改。 |
| 打开历史日记 | 单纯阅读不自动补写；通过手动命令或历史补齐操作处理。 |
| 手动命令 | 建议命名为 `Insert reflection into this daily note`，根据当前日记日期选文，避免在旧日记里误插今天的内容。非日记中不可执行。 |
| 插入位置 | 默认放在笔记属性区之后、正文之前；另一选项是文末。没有属性区时就是正文开头。 |
| 已有内容 | 插入后保存为普通 Markdown；升级内容库不自动替换旧日记中的文字。 |
| 可选问题为空 | 不显示问题标签、占位符或额外空段落。 |
| 日期不明确、标记损坏 | 保留原笔记并说明原因，不猜日期、不尝试扩大删除范围。 |
| 关闭自动插入或卸载 | 已有文字保留；批量清理由用户单独执行。 |

Daily Notes 的文件夹、日期格式和模板来自用户当前配置。V1 以核心 Daily Notes 为支持基线；不承诺自动识别任意第三方日志系统。核心功能未启用或配置不支持可靠识别时，给出简短说明，不启动设置向导。

设置页只包含自动插入开关、插入位置、历史补齐、批量移除和支持链接。自动行为不显示成功弹窗；手动和批量操作提供必要反馈。

### M1：先确认平台与产品规则

以当前[官方示例项目](https://github.com/obsidianmd/obsidian-sample-plugin)为参考，建立独立 TypeScript 项目、生产构建、测试与代码检查。清除示例功能，选择支持目标所需的最低 Obsidian 版本，不凭印象填写旧版本。

核实 Daily Notes 日期识别与模板完成时机。若参考旧音乐插件，只记录可借鉴的行为；代码复用需先确认许可证与适用性。该参考不是本项目的前置阻塞项。

名称与 ID 检查必须独立完成：搜索不到同名项目不等于可注册。官方要求名称和 ID 唯一，ID 的形式也有限制。[Manifest 规则](https://docs.obsidian.md/Reference/Manifest)

前置盘点桌面、iOS、Android 的可用测试设备或运行环境，避免到发布时才发现平台验证缺失。

### M2：固定内容数据，检验日期

采用 v0.4 JSON 作为输入，构建时校验并打包。为内容记录独立版本，使插件版本升级与内容版本可以分别追踪。

结构检查包括全部合法 MM-DD、唯一性、2 月 29 日、必填字段和 64 条空问题。日期测试覆盖平年/闰年、世纪年份、跨年、月份边界，以及本地日期与 UTC 边界，避免把笔记日期偏移一天。

内容 QA 继续检查近似正文、近似问题、拼写、说教感和容易误认为名人原话的表达；现有结构检查通过不代表这些编辑检查已全部完成。报告记录问题与结论，实质性内容更改另列供产品负责人判断。

### M3：先把一篇笔记改对

实现统一的生成段落识别与渲染，采用 Everyday Wisdom 自己的隐藏标记。命令和后续自动、补齐、移除操作共用同一套规则。

覆盖空文件、只有属性区、普通正文、有代码块、不同换行、可见标题被改写、多个标记、缺失结束标记等情况。代码示例中的标记不得当成待删除内容。

在修改时使用最新内容，正确处理编辑器中的未保存更改；同时触发多次插入时仍只保留一次。不会用旧的整篇快照覆盖用户刚输入的文字。插入和移除均验证操作范围外的文本保持原样。

这里完成后，应已能演示一个真正可安装、能手动插入的插件。

### M4：实现安装后自然工作的体验

接入新建日记与打开当天日记的事件，处理日记模板写入顺序和重复事件。验证核心模板；对常用 Templater 流程明确记录实际测试过的配置，不承诺兼容所有第三方脚本。

禁止每次打开笔记都扫描整库；按需识别目标文件。卸载或禁用时清理监听与任务，不再继续写文件。

隐私检查覆盖打包依赖：正常运行不发出网络请求，支持链接由用户主动点击打开，用户自己的 Obsidian 同步继续按其既有方式工作。双设备同时编辑的同步冲突要测试并说明，不承诺插件能代替同步系统消除所有冲突。

### M5：批量操作作为发布前的重点

补齐与移除先显示日期范围、候选数量、预计修改与跳过数量，再由用户确认。范围内不存在的日期不创建新笔记。执行过程中可取消，已完成、跳过、失败和未处理的结果分别说明。

移除只处理本插件的有效标记段落。缺失、嵌套或不明确的标记默认跳过。疑似被用户改写的生成段落也默认保留并在结果中说明，避免把写在卡片里的个人内容一并删掉。无关 callout、日记正文、属性、附件和音乐插件内容均不动。

用混合样本验证普通笔记、历史日记、已插入条目、手改段落、损坏标记、取消操作、读写失败及再次执行。移除确认框提供“同时关闭自动插入”（默认开启），完成后保存关闭状态；批量操作期间暂停自动插入。若用户选择保留自动插入，明确说明下次符合条件的创建或打开操作会重新添加，并验证这两种选择。

### M6：实际使用验证

测试矩阵至少包括：

- 桌面实际运行；iOS 与 Android 真机或能够运行真实 Obsidian 的受支持环境。
- 当前稳定版本；若声明支持更早版本，验证声明的最低版本。
- 默认主题深浅色、阅读模式与 Live Preview、窄屏、长标题、无问题条目。
- 键盘可完成设置和确认操作，提示文案简短可读。
- 默认/自定义日期格式、子文件夹、笔记属性、核心模板、重复打开、多窗口。
- 离线、重启、关闭自动插入、禁用/重新启用、升级后旧日记不变。
- 创建日记、手动插入、历史补齐、移除的完整流程。

手机窄屏截图不等于手机运行验证。缺少平台环境时，将其列为未完成的发布条件，不把桌面测试写成全部平台通过。除对应环境需要产品负责人配合外，其他开发与修复可以继续。

### M7：准备可以公开交付的版本

完成 README、使用说明、隐私说明、已知限制、更新日志、作者信息、支持渠道和许可文件。源码与内置文字的许可范围需要写清；MIT 可作为待确认的源码许可方案。官方要求提供许可证并遵守依赖许可。[开发者政策](https://docs.obsidian.md/community-directory/developer-policies)

引入[官方 ESLint 检查](https://github.com/obsidianmd/eslint-plugin)，运行类型检查、必要测试和生产构建。锁定依赖；让干净环境能够从发布对应提交构建出相同插件。官方审核也会检查构建及其对应源码。[审核 FAQ](https://docs.obsidian.md/community-directory/faq)

准备 `main.js`、`manifest.json`，以及实际需要时的 `styles.css`；可另附方便手动安装的 ZIP，但 ZIP 不替代正式附件。准备桌面与手机截图、短描述和完整介绍。

交付 `RELEASE_READINESS.md`：逐项功能状态、测试环境和结果、安装方法、内容版本、公开文件清单、已知限制。M7 通过表示产品已经可以提交发布，不表示审核已经通过。

### M8–M9：提交、修复反馈、验收公开安装

执行下文的提交步骤，处理每次审核反馈并重新测试受影响部分。只有实际完成目录发布和干净 vault 安装验收，才把 M9 标为完成。

## 4. 如何通过审核并上线

当前官方入口是 [Obsidian Community](https://community.obsidian.md)，GitHub 承载代码和 Release。按本次核对的[官方提交指南](https://docs.obsidian.md/plugins/releasing/submit-plugin)执行；正式提交时再确认入口没有变化。

### 第一步：准备归属于你的发布身份

你需要 Obsidian 账号、GitHub 账号和项目的归属信息。在社区网站登录后连接 GitHub，然后在 Plugins 页面使用 New plugin，填写仓库地址并选择 Owner。提交时需要同意开发者政策与维护责任；账号授权由你完成。[账号与提交表单](https://docs.obsidian.md/community-directory/set-up-and-claim)

作者显示名、仓库归属、许可证在对外发布前确定。支持链接是可选项，尚未准备好时不放占位链接，也不阻塞开发。

### 第二步：先把正式版本放到 GitHub

在你确认 M7 的具体发布材料后，发布源码和版本。建议初版插件号为 `1.0.0`；内容版本仍记录为 `0.4`。

检查仓库默认分支的 manifest 与 Release 一致，GitHub tag 与 manifest 的版本精确相同。发布附件分别包含 `main.js`、`manifest.json` 和需要时的 `styles.css`。不能只有源码或 ZIP。[发布与附件要求](https://docs.obsidian.md/plugins/releasing/submit-plugin)

### 第三步：填好社区条目

用 Everyday Wisdom 名称、简短功能介绍、README 与截图说明产品。描述真实支持的范围和英文内容定位。官方限制 manifest 描述长度为 250 字符，并规定基本格式；`minAppVersion`、移动端声明与实际实现一致。[提交要求](https://docs.obsidian.md/community-directory/submission-requirements-for-plugins)

### 第四步：查看自动审核，逐项修复

管理页会显示 manifest、发布附件、源码和构建验证的检查结果。Error 必须解决；Warning 与 Recommendation 也应阅读和处理或解释。

修复后增加版本并发布新 Release。必要时使用 Request review 或 Check for new releases。条目创建后，可用 Review branch 提前扫描候选分支，减少正式发布的反复。[审核管理](https://docs.obsidian.md/community-directory/manage-entry)

### 第五步：完成发布，再做商店安装测试

审核阻断项解决后，完成页面上的 Publish 流程，并核对实际条目状态。随后在新 vault 中从 Community plugins 搜索 Everyday Wisdom，安装、启用，创建日记并测试关键功能。这个步骤验证用户拿到的是公开发布版本，而不是本地开发版本。

### 第六步：保留维护入口

记录公开条目链接和发布版本，提供问题反馈渠道。之后通过新 GitHub Release 更新，仍处理新版本的检查结果；无需每次重新创建社区条目。[更新说明](https://docs.obsidian.md/community-directory/faq)
